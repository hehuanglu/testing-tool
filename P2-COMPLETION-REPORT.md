24 November 2026, ICT

## Architecture changes

### Before

The shared synthetic host and worker centered on native ZAP. The Bus Booking MockMvc and live launchers each prepared their own Git export, copied and checked the case matrix, verified the product contract, and managed teardown. The native product suite combined Maven, HTTP and offline HAR in its own runner and format. The historical ByteMe adapter had separate repository pinning, build and network ownership, an older case schema and a separate CI gate. Those lanes shared some report parsing and evidence conventions.

### After

- `ProjectAdapter.prepare()` owns source, build, fixture acquisition and teardown. The engine receives only the prepared inputs for its lane. The pilot shares immutable Git materialization, matrix validation and product contract verification. The synthetic adapter supplies an owned loopback fixture and an event observer. [Adapter contract](tests/security/security_framework/execution.py) · [Git materialization](tests/security/security_framework/project.py) · [Bus Booking adapter](tests/security/suites/bus_booking/adapter.py)
- The engine declares the capability and permitted suite methods. Shared admission runs before project preparation and the existing engine controls remain in place. MockMvc and live HTTP continue to observe response, identity and persisted state. ZAP continues to use bounded loopback native plans and its existing validation, process and report safeguards. The native product workflow runs the offline HAR lane and the compatibility engine validates its resulting evidence. [Engine contract](tests/security/security_framework/execution.py) · [Native scanner](tests/security/security_framework/engine.py) · [Product evidence adapter](tests/security/suites/bus_booking/native_evidence.py)
- V2 records execution, test assertions, criterion acceptance and capability qualification separately. Each witness names a producer and a JSON pointer in a hash-bound source artifact. V1 result shape, command exits and historical observations remain available. The product reader verifies the committed scope and suite digests, report and manifest agreement, criterion witnesses, HAR reconciliation, release blockers and cleanup. [V1 result schema](tests/security/security_framework/schemas/result.schema.json) · [V2 receipt schema](tests/security/security_framework/schemas/receipt.schema.json)
- The existing GitHub Actions workflow pins the triggering commit, Python and ZAP image. It records Docker and image platform, uses the observed shell exit, verifies fixture cleanup and stages only validated filtered bundles. The product-native workflow can be consumed through its existing filtered artifacts and retains its own gate. [Workflow](.github/workflows/security-suite-framework.yml) · [CI verdict contract](ci-verdict-contract.md)

The consolidation removes duplicated pilot Git export setup, suite matrix preparation and source inventory checks. It replaces fixture-specific resource unwinding at those entry points with shared admission and cleanup ordering. Historical feasibility and ByteMe entry points retain their existing execution and evidence. P3 can evaluate migration after a second project's resource and evidence needs are known.

## Remaining blockers and P3 readiness

- Bus Booking's release gate remains `MISSING`. P0/P1 recorded 18 PASS, eight REVIEW and two MISSING product objectives. The approved compatible passive baseline, 12 contract drift dispositions, product frontend and release environment evidence, and authenticated Active DAST qualification remain open. The shared Active DAST result is `BLOCKED` with zero dispatch. The product records it as `MISSING`.
- Bus Booking retains Spring and Maven, the exact API inventory, PostgreSQL and Mailpit, Java fixture shape, test identity roles, time policy and state oracles. The product HAR reader binds to its versioned policy and filtered report. The offline HAR runtime remains product-owned. The synthetic application-only path still uses the pinned worker image as a runtime container.
- The reference adapters exercise the shared lifecycle on in-process Java, packaged HTTP and the synthetic fixture, with a compatibility path for a native product suite. A second product still needs its own lifecycle, dependency and fixture review and qualification. Unknowns include cross-platform image equivalence, runtime and identity readiness for another stack, evidence producer mapping and resource correlation under a different deployment topology.
