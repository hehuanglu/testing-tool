# Security test specification

## Objective and traceability

**SEC-A01-01 · CWE-862 — Missing Authorization.** Authenticate requests to protected APIs before processing. Administrative operations require ADMIN or SUPER_ADMIN. Role modification requires SUPER_ADMIN. A missing guard can expose protected data or permit writes by a principal without the required role.

The pilot covers the 25 protected method-and-path pairs in the Bus Booking API contract. The project maintainers own the test and its disposable local fixtures. The implementation uses the clean security-CI checkout at `56f58a3ed86d22d44bd2007e3a49aeb0c979510f`. Runtime provenance records the actual commit, hashes for the API design, OpenAPI, POM and Java fixture, and the Java, Maven and PostgreSQL versions. The pinned project declares Spring Boot 4.2.0 and JJWT 0.13.0.

The policy oracle comes from [API design, sections 4.2–4.4](https://github.com/maaL6/bus-booking-system-phase-2/blob/56f58a3ed86d22d44bd2007e3a49aeb0c979510f/docs/04-api-design.md) and the supplied objective. OpenAPI supplies method-and-path inventory. The API design documents omitted 401/403 responses and the 200/201 discrepancies for booking and catalog create routes. The matrix uses the documented 201 behavior for create operations. Spring Security matchers, JWT verification and user loading, the controllers, Flyway role rows and the privilege service were reviewed for fixture compatibility and observed behavior.

## Test design

- The [authorization matrix](../plans/authorization-matrix.txt) declares paths, roles and expected HTTP status independently of the production matcher. The launcher checks all 32 pairs against the pinned OpenAPI inventory.
- The [fixture](../fixtures/BusBookingAuthorizationPilotTest.java) starts the real Spring application context with MockMvc, the production security chain, controllers, services, repositories and Flyway migrations. The application has no TCP listener. A new temporary PostgreSQL container exposes an ephemeral loopback-only database port. The email sender alone is mocked. The fixture follows the project’s existing AuthHttpIntegrationTest, ProfileAndRolesIntegrationTest and catalog/booking integration tests for the test profile, fixed clock, BCrypt and PostgreSQL fixture patterns.
- Four preverified fixture identities log in through `POST /api/auth/login`. A separate `GET /api/auth/me` with each issued token must resolve the database-seeded account and expected role. No HTTP session is expected. No principal or authority is supplied by the test harness. A target USER and a pending account are used only as fixtures.
- Each protected matrix cell receives fresh catalog, trip and booking state. Booking starts with one confirmed seat and nine available seats. Booking creation consumes two seats and cancellation restores one seat. Trip updates and cancellation get a scheduled trip without bookings. Vehicle updates get a vehicle without trips so the catalog identity-lock rule does not interfere with the role control. Role writes use a distinct active and verified target. Profile assertions compare the result and independently read the assigned account from PostgreSQL.
- Route-level rejection requires the expected JSON status, error/path, no selected MVC handler, no projected sensitive fields and unchanged persistent rows. Booking ownership and role business rules run within the selected controller and still require unchanged rows on denial. Each allowed operation checks a specific response field or fixture ID, plus expected database state. Positive role controls use the same operation and valid inputs as denied cells.
- The clock is fixed at `2026-11-01T00:00:00Z`. Fixture passwords and PostgreSQL credentials are generated per invocation. Cleanup removes the exported checkout and this invocation’s database container. The app test process is bounded to 180 seconds. The scanner restriction checks require no runtime fixture.

## Test cases

All IDs map to `SEC-A01-01` and `CWE-862` in the [registry](../cases/cases.json). The [request plan](../plans/authorization-matrix.txt), [profiles](../authentication/profiles.json), [launcher](../adapter.py) and [oracle](../assertions/oracle.py) are suite-local.

| Case ID | Conditions and expected evidence |
| --- | --- |
| BB-AUTH | Real login and current-user proof for four distinct identities. Missing token, malformed scheme value, expired fixture token, duplicate headers, inactive account, unverified account and bad password return 401. Public locations succeeds anonymously and rejects an invalid Bearer. Restoring the account re-enables the same legitimate token. |
| BB-PROFILE | Auth/me and profile GET/PUT use the matrix. All signed-in roles see their own account. Successful PUT stores the changed name and phone and retains the account role. |
| BB-USER | USER can create a booking and list personal booking history. Other roles require the applicable 401/403. Successful creation persists a booking for the principal and decrements inventory by two. |
| BB-BOOKING | Booking owner, ADMIN and SUPER_ADMIN can read or cancel the fixture booking. Anonymous and a second USER are denied. Successful cancellation persists CANCELLED and restores the seat. |
| BB-ADMIN-READ | Each of six administrative list operations returns the seeded resource for both privileged roles. Anonymous and USER are denied before MVC selects a handler. |
| BB-ADMIN-WRITE | Each of eleven administrative resource writes uses valid fixture data, returns the expected status and resource fields for both privileged roles and persists the expected values. Denied rows leave state unchanged. |
| BB-ROLE | Only SUPER_ADMIN can promote the distinct target from USER to ADMIN. Verify target ID, returned and stored role, and the sole SUPER_ADMIN invariant. |
| BB-ROLE-LIFECYCLE | Verify ADMIN access, demote to USER through the API, replay the same issued token, require 403 on the admin route and 200 with unchanged subject and updated role on auth/me. Restore ADMIN through the API and verify stored role. |
| BB-ROLE-RULES | SUPER_ADMIN cannot change its own role (403), assign SUPER_ADMIN (400) or promote an unverified target (409). Require expected JSON and unchanged persistent rows. |
| BB-SCANNER-JWT | Shared-runner JWT capability yields BLOCKED with `AUTH_PROFILE_UNQUALIFIED` and a no-dispatch receipt. |
| BB-ACTIVE | Active execution yields BLOCKED with `ACTIVE_EXECUTION_RESTRICTED` and a no-dispatch receipt. |

Application evidence keys are `provenance`, `jwtAcquisition`, `jwtIdentity` and the case ID. The [Java fixture](../fixtures/BusBookingAuthorizationPilotTest.java) specifies exact synthetic request bodies, substitutions and SQL readback. The matrix determines actor, method, path and expected status. The case evidence records the operation and actor aliases, observed and expected status, handler selection and its expected value, response predicate and state predicate. The internal arrays never retain payloads, IDs, JWTs, passwords, phone numbers, or database contents.

## Execution, evidence and verdict

A **PASS** requires complete, valid rows, verified identities and every expected response and state predicate. A **FAIL** requires verified identity and a complete, usable case receipt with an observed contract mismatch. **ERROR** covers wrong identity, invalid or incomplete evidence, contract inventory drift, startup/process/timeout/cleanup failure or unavailable prerequisites. **BLOCKED** requires the shared capability boundary’s unmodified no-dispatch receipt. Shared severity is ERROR, BLOCKED, FAIL, PASS and exit codes are 2, 3, 1, 0, respectively.

Two clean baselines establish repeatability. Controlled changes to copied projected observations verify oracle handling of status, state, handler dispatch and identity mismatches. No application authorization rule is disabled by a control. The CI gate retains only projected JSON and Markdown.
