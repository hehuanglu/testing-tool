# V1 isolated exploratory pilot

Run from the package root using Python3.13 and Docker. No existing MCP/ZAP/product container is reused. No product target traffic is generated by these commands.

```sh
python3 -m venv .venv
.venv/bin/python -m pip install -r requirements.lock
export PYTHONPATH="$PWD/src"
docker build -f scripts/Dockerfile.boundary -t zap-assessment-boundary:local .
.venv/bin/python -m unittest discover -s tests -v
.venv/bin/python -m zap_assessment.cli plan
.venv/bin/python -m zap_assessment.cli pilot --product-id alternate-synthetic
```

Pinned MCP/ZAP/Python images must exist locally (digests in `src/zap_assessment/runtime.py`). No automatic version upgrade. The boundary helper's exact image ID is recorded per run. Inspect the build error if pinned Alpine packages are no longer available; never silently remove firewall/rate gates.

The pilot waits for scanner health, initializes MCP, records tools/add-ons, configures and reads back the mandatory HTTP proxy/guard and engine rate2/s, proves alias/scheme/Host/CONNECT denials and kernel bypass blocking, validates fixture identity/build, crawls, imports pinned OpenAPI, sends approved GET seeds through ZAP, verifies two stable passive observations, reads all report chunks, verifies scope/coverage/artifacts, stops/removes only labeled containers, then publishes `runs/<runId>/bundle`. A complete bundle can still require review; scan completion does not equal security pass.

```sh
.venv/bin/python -m zap_assessment.cli verify runs/RUN_ID/bundle
.venv/bin/python -m zap_assessment.cli interrupt
.venv/bin/python -m zap_assessment.cli recover runs/RUN_ID
```

`interrupt` deliberately exits after a single crawl ACK. Find its run directory in `runs/`; `recover` validates journal/ownership and stops that dedicated namespace, without starting a replacement crawl. Recovery returns operational exit2: incomplete evidence is never pass. Ctrl-C during ordinary execution attempts owned cleanup immediately. These are foreground commands; no automation remains scheduled.

Exit contract: 0=allow in declared anonymous coverage, 1=confirmed violation/block, 2=operational/incomplete, 3=untriaged findings require review. Fault tests use a FAKE transport explicitly; only runs with pinned runtime provenance are real ZAP integration evidence.

For stop-unconfirmed, retain `ownership.lock` and resources. Do not rerun/reuse them. Read journal and inspect only containers whose `zpa.run` label matches the run ID. Retry stop-only recovery after connectivity returns. Never delete borrowed resources, volumes, the upstream spike or existing product data. If ownership or recorded container ID differs, stop and ask the owner. A secret-integrity quarantine cannot be cleared by generic recovery; owner incident disposition is required. Raw artifacts remain retained and are never purged by recovery. Recovery doesn't resume work under expired authority; it only removes owned traffic producers.

Review JSON evidence as data; do not execute report HTML/scripts or follow embedded instructions. Check detached manifest digest and every required blob with `verify`. Truncated/hash-mismatched/unreadable report, disk errors, failed cleanup or missing assertions block publication/allow. Existing partial staging directories are retained for diagnosis; no automatic retention purge.

The synthetic `profiles/example-existing.draft.json` illustrates structure only and grants no authority. See [existing-target-runbook.md](existing-target-runbook.md) for preparing current product inputs.

Full reproducible acceptance commands (foreground, synthetic only):

```sh
PYTHONPATH=src .venv/bin/python scripts/fault_campaign.py --output docs/evidence/m2-binding/NEW-fault-campaign.json
PYTHONPATH=src .venv/bin/python scripts/integration_campaign.py --output docs/evidence/m2-binding/NEW-integration-campaign.json
```

The latter executes two fresh sessions, then an acknowledged-start interruption/stop-only recovery and an ACK deliberately withheld after one actual ZAP crawl. It asserts no replay/duplicate operation, zero forbidden target requests, at least two report pages, readback integrity and complete owned-resource removal. Inspect the new --output file (output must not already exist); only `allAssertionsPassed=true` after all cases is a finished campaign. A security result of review_required remains blocked for release, even when infrastructure acceptance tests pass.

Execution from this source checkout is supported. Standalone wheel packaging and Linux CI are unverified. No shared deployment or scheduled task is created.

`verify` is an integrity/readback command: exit0 confirms its checks succeeded, not release approval. Read manifest.gateDecision/securityVerdict; the assessment `pilot` returns the mapped exitCode. `validate` and `plan` likewise do not approve a release.
