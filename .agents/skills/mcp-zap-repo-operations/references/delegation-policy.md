# Subagent roles and delegation decisions

Use within the single [criteria workflow](criteria-driven-workflow.md), with one coordinator responsible for the assessment and its [Drive output](single-table-drive-output.md). Roles below are task instructions for available host subagents, not separately installed agents or an automatic worker scheduler. Delegation never grants product traffic, secret access or broader effects.

Apply the [agreed assessment policy](assessment-policy.md): the coordinator may use subagents whenever they fit the testing work; no separate budget-justification or knowledge-authenticity review is needed. User knowledge/catalog is the standard.

## Decide before spawning

Use one preparation subagent for the preparation/revision loop below. For other tasks, keep the work with the coordinator when it is a short, coherent case/readback, depends on immediate shared state, or handing over context would duplicate more work than it saves. Do not create one agent per criterion, role, tool or table row. Skill-only maintenance/status tasks do not require a product preparation agent.

Delegate a bounded task when at least one concrete benefit exists:

- Discovery spans a distinct business area with its own source/spec and a useful independently reviewable inventory.
- A substantial compatible case group needs specialized UI/auth/protocol/fixture context that can be isolated from unrelated history.
- Results need a fresh evidence review because one observation supports materially different criteria, broad met/N/A claims or the effect of method limits on pending obligations depend on interpretation, or source/policy/readback conflicts could change conclusions.
- Final delivery has a reviewed snapshot and a bounded range write or projection task that can be handed off without duplicating verification.
- The coordinator has persisted the necessary state, but unrelated accumulated context would obscure the next coherent task. A fresh worker can load selected facts instead of repeating the assessment or asking the user to change chats.

State the task objective, expected benefit, read/write/effect boundary and requested return before dispatch. Use only as many workers as have distinct ready tasks and valid resource ownership; do not spawn a fixed team for a small assessment. Capacity depends on host availability and measured executor constraints, not catalog row count. Existing approvals remain valid for their exact delegation scope; reusing an allowed worker boundary adds no per-worker approval.

## Model and reasoning at dispatch

Select the profile by the most demanding decision in the assigned brief. The model of the coordinator's chat does not determine worker configuration. On hosts with spawn overrides, pass the exact `model` and `reasoning_effort` below and set `fork_turns: "none"`. Load the brief and referenced skill sections in the fresh worker. A follow-up to the same worker keeps its original configuration.

- **Preparation and revisions — `gpt-6.1-sol` / `high`.** Start here for the whole two-gate role. Use `xhigh` when ambiguous requirements, cross-product boundaries or conflicting product facts materially affect the plan. Keep both gates and routine revisions with the same worker. If an unresolved issue needs a stronger model, give a separate focused review to that profile or replace the preparation worker with the retained draft and feedback if it cannot continue effectively at its current configuration.
- **Discovery — `gpt-6.1-terra` / `medium`** for source-grounded inventory and tracing across an identified area. Use `gpt-6-luna` / `low` for mechanical extraction from specified files or a stable inventory with an exact output shape. Use `gpt-6.1-sol` / `high` when discovery requires inferring auth, trust, ownership or state boundaries across conflicting sources.
- **Execution — `gpt-6.1-sol` / `medium`** for a bounded approved group with established controls, executor and readback. Use `high` for stateful auth, BOLA, browser journeys, protocol ambiguity, or effects whose status requires semantic reconciliation. A purely read-only lookup of exact retained IDs can use `gpt-6-luna` / `low` if raw evidence and provenance are preserved and interpretation stays with the coordinator.
- **Evidence review — `gpt-6.1-sol` / `high`.** Use `xhigh` for material conflicts across policy, source and runtime or a consequential broad verdict whose sufficiency is disputed. Mechanical reference matching can use Luna low as evidence collection under the execution profile.
- **Assigned skill or tool maintenance — `gpt-6.1-terra` / `medium`** for bounded code, tests or documentation changes. Use `gpt-6.1-sol` / `high` for audits or repairs spanning authority, executor admission, evidence linkage or recovery contracts. Keep fixes to isolated worker-owned files or coordinate edits with the canonical owner.
- **Drive delivery — `gpt-6-luna` / `low`** for preparing a deterministic projection or applying approved values and formatting to an existing, explicitly bound range. Use `gpt-6.1-terra` / `medium` for a bounded projection or formatting repair requiring code. Resolve semantic discrepancies and uncertain write outcomes with the coordinator before further writes.

If a preferred model is unavailable, choose Sol at the assigned effort or higher when the host supports it. If explicit overrides are unavailable, use the host default only if it is suitable for the task and record that fallback. Keep optional work local when no suitable worker is available. Preserve the preparation dependency rules below. Record the selected profile, actual fallback and material escalation in existing private task notes. A model change never supplies approval or changes packet, lease or replay rules. If a worker reaches decisions outside its brief, return the unresolved decision and retained evidence to the coordinator. Reconcile uncertain effects before any reassignment.

## Coordinator

The coordinator maintains the full catalog/criteria-to-case map, product model, actual approval sources/revisions, canonical working RUN, journals/resources, final criterion conclusions and delivery status. It is the sole writer of canonical assessment state and owns official Drive publication. Only the bounded delivery worker below may apply an approved write on its behalf. Workers can write task-owned private results and executor journals. Canonical RUN and final conclusions stay under the coordinator’s write authority.

The coordinator reviews the preparation agent's work rather than accepting its self-assessed readiness. It owns the internal pass/revise decision and the questions needed to resolve actual weaknesses; the preparation agent owns draft authoring and revisions. The coordinator may provide facts and corrections but does not silently replace the worker's draft and count that as the worker having resolved the review.

Before assigning, check overlap with already assigned/answered cases and the resource map. Merge verified facts into the shared product model so later workers reuse discovery, login/fixture mappings and retained observations. The coordinator continues useful independent work while a worker runs; it never claims background monitoring merely because a worker was spawned.

## Preparation subagent and coordinator review

Assign one coherent preparation task in a fresh context, with references to the supplied catalog, authorized project/environment, applicable skill guidance and retained working state. The preparation agent needs access to the complete assigned catalog through its source reference so it can reconcile coverage; do not paste the full transcript or secrets into its prompt. Its working artifacts remain private drafts. It may inspect authorized source/spec/config for basic reconnaissance; this role alone does not authorize live discovery, scans, login or fixture mutations. Any necessary live facts are obtained within existing authority and resource controls, coordinated by the main agent.

First the preparation agent normalizes the catalog without replacing original wording or the user's expected protection. It returns product-grounded criterion interpretations, finite testing questions and sufficient observations, together with relevant facts, assumptions, method/access/fixture dependencies and unresolved interpretation. The coordinator reads the draft against the actual catalog and selected underlying product facts, chooses the questions that matter for this situation, and sends weaknesses or missing support back to the same preparation agent. The agent investigates within its boundary, revises the draft and answers the feedback with supporting references or an explicit dependency. Repeat until the coordinator judges this draft fit for catalog review, then present Gate 1. Do not prepare the test plan ahead of the catalog approval.

After Gate 1, the same preparation agent uses the approved interpretations and further relevant discovery to draft the executable shared work plan required by the canonical workflow. The coordinator audits whether that plan can answer the assigned questions with the actual product, techniques, executors and observations. Select review questions from the demonstrated risks and uncertainties; there is no mandatory question list, role/input Cartesian product, scoring rubric or number of revision rounds. A generic technique name, endpoint interaction count or helper success cannot by itself establish that the plan is adequate. Where relevant, investigate such issues as a missing valid baseline, an unsupported authenticated body, an unreachable business state or a source-only requirement being assigned a runtime test; these are examples, not a fixed checklist.

Before passing the plan, audit evidence sufficiency at the case level. For each case, trace the criterion through the selected product path and runtime conditions to the observation that would support or contradict it. Shared operations may reuse the same trace, but each mapped criterion needs its own evidence rationale. The coordinator checks the relevant source, config, spec or executor contract and asks the preparation agent to resolve any mismatch in the draft. Keep these checks proportional to the case, using questions such as:

- Does the chosen route actually expose the input, actor or object relationship that the criterion requires? Trace a caller-controlled selector to the lookup or write predicate. An address type resolved within the session owner's records cannot exercise access to another owner's record. Use a real foreign selector with a valid owner baseline and an independently valid non-owner.
- What other condition could produce the same response? Require controls that distinguish the intended mechanism. For server-side expiry, send the same previously valid token after the recorded deadline and use a still-valid session as a control. Browser cookie omission, revocation and rotation answer different questions.
- Can the planned build, origin and effective configuration produce the required observation? For a Secure cookie in an HTTPS session, identify the HTTPS endpoint, TLS termination, application mode and relevant cookie writers. Record what HTTP or source evidence can establish. If the required runtime is unavailable or outside the envelope, mark that observation pending with the exact prerequisite and reopening action.

Also audit what the draft could have missed. Independently compare the preparation agent's planned surface with available product sources such as route registrations, API descriptions, browser journeys, proxy rules and role/state boundaries. Ask which relevant operations are missing, reachable only under a different actor or state, or supported only by source. Trace each criterion to its bounded population and each discovered relevant surface back to a planned case, an explained representative group, an applicability or scope basis, or an unresolved dependency. For universal criteria require an exhaustive bounded inventory. Record candidate inventory, intended ZAP coverage and actual observed coverage separately. Reconcile the actual inventory after authorized discovery, within the approved envelope, before using scan results as coverage.

Challenge technique selection against the installed or discoverable ZAP capabilities and the product. For each distinct evidence gap, ask what additional safe exploration or probe would close it, what observation that technique adds, and what prevents it from working. Consider browser journeys and browser-based crawling for client routes, scoped specification import for APIs, passive rules for observed traffic, selected active rules for eligible inputs, and Requester or bounded fuzzing for exact actors, inputs and state readback. Compare native alerts and tester observations separately. Treat import and crawling as potentially traffic-generating. Verify method, redirect, origin, auth, fixture and effect guards before use. If a technique adds meaningful coverage but its capability or prerequisite is unverified, record the verification, fallback and remaining evidence gap. Skip redundant or unsuitable techniques with a product-specific reason.

Return inadequate cases with specific questions or corrections. The preparation agent revises the case, mapping, evidence units or dependency and cites the product or executor facts used. The coordinator independently checks those facts and the revised case against the criterion before accepting it. Generic evidence labels or a structurally valid plan cannot settle a disputed oracle. Pass the current draft only when substantive concerns are resolved, planned executable work has concrete readback, and remaining dependencies identify affected obligations and next actions. Review pass establishes preparation readiness. Present Gate 2 only after that internal pass, and execute only under the actual approvals and admission contracts.

Retain the reviewed draft revision/reference, material questions, responses/changes, open dependencies and the coordinator's pass/revise basis in private preparation notes or existing working-state details. Use an ordinary source/discovery brief before approvals: `make_packet` requires an approved plan and is not an intake/planning API. This is an agent-operated review loop, not a new enforced JSON schema, automatic quality oracle or extra approver-signature requirement. Existing user instructions/waivers still govern business approvals; they do not make inadequate preparation sufficient.

On continuation, reuse the retained reviewed preparation and compatible approvals. Return only missing or materially affected preparation to this role; do not restart a sound catalog/plan merely to use a new worker. If the worker fails, preserve its drafts and unresolved feedback and resume or replace that one preparation role with the same scoped references. If a preparation worker is unavailable, retain that concrete dependency, continue independent authorized work and retry when available; do not silently waive the assigned role/review or claim it passed.

## Discovery worker

Partition by business area/security boundary (for example document sharing or account/session lifecycle), not by catalog row. Assign relevant catalog excerpts plus boundary facts; do not paste the full transcript or unrelated catalog. A worker can identify additional criterion relationships as proposals without expanding approved scope.

Return discovered method/operation/journey, auth/role/object/state/consumer boundaries, facts with exact source locations, assumptions, missing source scope, candidate questions and prerequisites. Distinguish supplied inventory from independently inspected sources. Source discovery supplies no dynamic coverage or final applicability/verdict.

Before criteria/plan approval, use a read-only discovery brief naming source paths, allowed inspection and required result. The v2 make_packet API requires approved criteria and plan and is not an intake discovery API. No live discovery is added to a source-only brief; any authorized live discovery needs its own explicit target/effect boundary. For assigned skill-only maintenance/review, the brief concerns skill sources, not a product assessment or invented product approvals.

## Execution worker

Assign a compatible group of questions/cases sharing target/build, actor/session, fixture/state, technique and required observation stage. Reuse one actual operation across mapped criteria only through compatible evidence links. Keep distinct expectations/stages as distinct obligations even when their operations overlap.

Use the approved v2 packet/admitted executor, resource leases and durable intent/ACK/readback contracts in [the canonical workflow](criteria-driven-workflow.md#delegation-and-shared-state). Include selected approved fixture/fallback/cleanup/limitation and oracle context through permitted references; IDs alone do not suffice. Worker private output and the receiving executor must preserve original ACK/native IDs/results before reporting success.

Return actual operations, compatible observations, proposed case outcomes, errors/missing units, pending effects and owned resource disposition. A missing observation remains missing; do not issue substitute effects or change the oracle to complete the task. The coordinator checks raw-to-semantic correspondence and derives criterion verdicts after merge.

## Evidence-review worker

Use focused review when it helps the coordinator interpret testing observations; it is optional tester assistance, not an independent validation of user knowledge or a mandatory finalization gate. Do not insert a mandatory independent signature for every case, routine readback or assessment. Give original criteria/oracles, approved relevant plan, candidate conclusions and direct readback/source references. Do not provide only the executor's summary or instruct the reviewer to reproduce a preferred answer.

The worker reads existing evidence and checks sufficiency, context, counterexamples, missing siblings, provenance, applicability and unjustified reuse. It proposes supported/unsupported conclusions and exact missing facts; it does not dispatch a scan, refresh/login, mutate fixtures, approve a plan or publish the table. It may recommend a necessary test; only the coordinator schedules it within approved scope.

A separate worker gives a fresh interpretation, not guaranteed independent evidence or an automatic semantic oracle. If review tools/capacity are unavailable, the coordinator performs and records the focused checks itself; lack of a reviewer alone is not a security criterion's not_evaluable reason. An actual evidence conflict stays open until resolved from authoritative policy and context-compatible observations, not majority vote.

## Drive delivery worker

Use optionally at final delivery or for a user-requested table synchronization when a reviewed snapshot is ready and delegation saves work. The coordinator creates or resolves the existing file and binds its run, worksheet and exact managed ranges. Give the worker sanitized, reviewed values and formatting instructions, with the source revision, file ID, worksheet ID, allowed ranges and applicable Drive/Sheets skill references. If the worker lacks the connector, it can return the private projection for coordinator publication.

The worker applies only the specified values and formatting. Return the affected ranges, write receipts and any uncertainty. File creation, interpretation of evidence, verdict changes and marking delivery verified stay with the coordinator. Sharing remains user-managed. Allow one writer at a time. The coordinator independently reads back the complete managed table and checks the delivery specification before updating private delivery state. An uncertain write returns to the coordinator for reconciliation before another attempt. First establish that the previous writer and any in-flight write can no longer change the range. Read back the bound range against the reviewed snapshot. If the write may still land, keep delivery pending and avoid a competing writer. This assignment uses the existing Drive publication authority and a delivery brief; it does not use a product execution packet or lease.

## Context, results and API boundary

Use a fresh context for each new unrelated task (`fork_turns: "none"` where available). If the host cannot isolate context, keep optional work local when a fork would copy substantial unrelated history. Keep the same worker for a coherent revision loop and send only the changed facts, unresolved questions and current artifact revision.

Give the worker a short brief with its objective, selected criteria/cases, oracle, authority and effect boundaries, resource ownership, prerequisites, expected output and stopping conditions. Point to exact skill sections and private artifacts using a path or tool reference plus a locator such as a criterion ID, journal operation ID, section or range. Load those portions first. Expand only for a concrete missing fact, recording material dependencies. Keep raw payloads, transcripts and secret values out of messages. Pass private secret references only when the assigned executor requires them.

- Preparation reads the complete assigned catalog when reconciling coverage, then the relevant product sources and current draft. Revisions load the affected sections and feedback.
- Discovery and evidence review read the selected catalog clauses and source or direct readback needed to substantiate each finding. Include the original oracle and approved conditions for evidence review.
- Execution loads the selected approved packet and the referenced fixture, fallback, cleanup, limitation and pending-effect details for its cases. Reconcile an uncertain effect against the relevant native and journal records before dispatch.
- Maintenance starts with the reproduction, expected behavior, relevant files and focused verification. Expand to neighboring contracts when the fix could affect them.
- Delivery reads the reviewed projection by managed range and revision. It needs the bound file and worksheet IDs and formatting instructions.

Store detailed drafts, logs and results in task-owned private artifacts. In the worker's final message return task ID, status, material findings or changes, artifact references with locators, pending effects or held resources, and the next action if any. The coordinator reads the exact portions needed to verify and merge. Pass an artifact reference and the relevant change summary to subsequent workers.

Discovery, review and delivery briefs and their results are task-owned artifacts or messages, not inputs to merge_result. The current merge API accepts only its binding fields plus operations/caseResults; it does not accept arbitrary discovery/review/pendingEffects/resourceDisposition keys. The coordinator interprets discovery/review output and records pending/resource facts through existing RUN/journal structures under the canonical writer lock. Do not add unsupported packet fields or JSON-imported handlers to simulate a role API.

Validate the task/revisions/digests, each operation/evidence reference, context and required observation before accepting output. Reconcile divergent facts from sources and actual readback; retain disagreement and request exact missing evidence rather than averaging worker confidence. Stale output remains historical until compatibility is reviewed. Never overwrite conflicting case history merely to make merge succeed.

Use [subagent operations acceptance](operational-validation.md#subagent-operations-acceptance) when changing or qualifying these workflows.

## Scheduling and failures

Read-only discovery/review tasks may run concurrently when they only read stable retained snapshots. Execution sharing a scanner, session, policy, fixture, object state or attribution history runs sequentially unless all affected resources are explicitly isolated. A fresh agent context or a different URL is not resource isolation. Use the same coordinator state directory and consistent scanner/session/fixture resource IDs for cooperating executors; leases cannot protect unrelated callers that bypass this protocol.

A worker finishing, timing out, failing or being interrupted does not prove an effect stopped. Read the retained journal/ACK/native status and exact object state; reconcile before lease release/replacement or new effects. No timed lease takeover or consumed/unknown action replay by a replacement worker; genuinely missing work may continue on a valid new allocation within the approved envelope. Preserve valid earlier observations and continue independent ready tasks.

### Retire workers after handoff

Reuse a worker only for an active coherent task or its pending revision loop. Keep the preparation worker through the two gates when it can continue. Save the draft and feedback before waiting on either gate. If the host cannot retain the worker, resume the same preparation role from those artifacts after the gate decision. After a worker finishes, verify its retained output, persist accepted results or unresolved dependencies, reconcile pending effects and release leases only when safe. Then stop assigning work to that worker and close it if the host supports closing. A finished worker can be left idle on hosts without close support. Closing or interrupting a worker does not delete retained artifacts, free a lease or establish that native activity stopped.

If a worker stalls or needs replacement, save its current artifact references and unresolved question first when available. Interrupt only when needed, reconcile its effects and leases using the rules above, and give the replacement a fresh brief with the exact outstanding work. Never replay an unknown effect or remove journals, evidence, drafts or historical state as part of retiring a worker.

For execution or optional discovery/evidence review, when no safe worker/executor is available, continue sequentially if feasible; this fallback does not waive the preparation role/review above. Checkpoint only for the actual conditions in [recovery](retention-stop-and-recovery.md), with canonical state, pending-effect references and next action saved. Worker completion is a local progress event, not assessment completion or a reason to ask the user to continue.

## Managed coordinator writes

Workers return bounded result files, drafts or repair proposals. The coordinator reviews them and commits canonical state with an expected generation. Preserve original packet and resource bindings for readback and cleanup. Use shared resources sequentially unless the actual isolation is established.
