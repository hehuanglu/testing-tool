# MCP ZAP Server implementation and extensibility audit

## Decision

**Guided mode is an intentional architectural boundary.** The server registers four guided tool services by default and adds expert groups only when the deployment selects the expert surface. Separate authorization and policy checks then govern calls to registered tools. The running container explicitly selected guided mode and the previous authenticated discovery returned its 21 tools. The absence of expert tools on that instance is a deployment choice. Several lifecycle and evidence operations remain incomplete even in the expert source. [Registration][registration] · [Surface configuration][config] · [Authorization and protection][governance] · [Runtime evidence M01–M02][evidence]

The local checkout also exposes **source-to-image drift**. Both identify as 0.16.0, but the checked-in attack method declares two input fields absent from the captured live schema. The checkout also contains an experimental JSON bearer provider that the live audit did not qualify. The running images lack an OCI source-revision label. The source findings in this report apply to repository commit `e8197caab2d530287214b0e7b8231a3691e0bba8`. Runtime findings apply to the observed images and tool schema. Establishing a reproducible build-to-image mapping is the first roadmap item. [Checked-in attack schema][guidedattack] · [Experimental provider][jsonswitch] · [Runtime discovery][evidence]

The architecture can accommodate more native ZAP capabilities through typed adapters and scoped MCP tools. The strongest route for reusable defensive regression is to use MCP for authoring assistance, scoped fixture verification and evidence inspection, with repository-owned tests and reviewed plans executed by an independent CI runner. This design keeps application assertions under version control and gives CI a process result, captured fixture observations and reproducible artifacts.

## Evidence and execution architecture

This audit inspected the bundled Java server and its configuration, cross-checked the running container's non-secret settings, and reused the previous fixture runs. Both containers reported healthy. The current image reported `guided`, API-key authentication, a single-node queue coordinator and disabled inline OpenAPI staging. No auth profile environment overrides were present in the inspected configuration projection. The source defaults to an empty profile list, and prior runtime evidence rejected a synthetic profile and session. These facts establish the missing fixture binding for that audit. They do not inventory every possible operator configuration source. This was a read-only implementation audit. No Java, deployment or application changes were made, and no new target calls or tests were run. [Defaults][config] · [Prior capability report][capability] · [Evidence B01–B02 and C10][evidence]

The request path is **MCP client → Spring AI WebFlux tool callbacks → gateway authorization and operational protection → domain service → typed ZAP adapter → ZAP sidecar**. The checkout uses Java 25, Spring Boot 4.1.1, Spring AI 2.0.1, MCP gateway 0.11.0 and ZAP Java Client API 1.17.0. The service wires a `TimeoutZapClientApi` wrapper with configurable connect and read timeouts. Its internal component/method dispatch is available to trusted Java code. MCP callbacks expose only registered methods. Adding a client-callable capability requires a tool and authorization contract in addition to any SDK operation. Engine add-ons remain a separate dependency of the running ZAP process. [Build dependencies][build] · [Gateway version][gatewayversion] · [Client wiring][clientconfig] · [Timeout transport][transport] · [Authorization scopes][scopes]

Guided execution selects direct mode by default and prefers queued mode when the job store is PostgreSQL or coordination uses PostgreSQL locks. The prior fixture used direct execution. The source has typed ports for scan execution, contexts, findings, reports, imports and plans. It also exposes policy and evidence metadata hooks as public extension contracts. Those hooks do not register arbitrary new MCP tools. A new scanner operation would typically need a core adapter, service, explicit callback registration, scopes and a deploy-time capability check. Workspace ownership in the gateway and a dedicated ZAP engine/session are distinct controls. [Execution routing][mode] · [Scan port][scanport] · [Context port][contextport] · [Native adapter capabilities][adapter] · [Extension contracts][extensions]

## Gaps and proposed architectural changes

Complexity estimates describe implementation and qualification. **Low** means reusing an existing adapter or configuration. **Medium** includes a new contract and integration tests. **High** includes engine lifecycle, multi-tenant or cross-process behavior. Fixture strategies below are proposals. They use benign local requests, configuration readback, synthetic artifacts or a recording adapter. The prior AI execution boundary prevented live active DAST qualification. That boundary is independent of the server's API and tool registration.

### 1. Target authentication and session lifecycle

**Root cause and existing implementation.** The guided contract exposes prepare and validate by operator-defined profile ID. The resolver compiles profiles at startup, binds them to one origin and resolves server-held credential references. It does not expose profile authoring or a general session settings API. The form provider creates a scoped context and user, sets auth method and login indicators, and additionally configures auto-detect session management for browser profiles. Form validation uses ZAP's authentication diagnostics. Browser validation can return unconfirmed. Neither justifies claiming a particular effective application subject in the audited deployment. Static bearer and API-key profiles are reference-only in this checkout, with no engine binding or protected request verification. [Guided auth tools][authtool] · [Profile resolution][profiles] · [Form and browser provider][form] · [Header reference provider][header] · [Authentication diagnostics][diagnostics]

**JSON, header replay and renewal.** The checkout's conditional JSON bearer provider configures native JSON login and header-based session management. Validation can use a protected endpoint with a subject or signed identity check, or a generic auth result. The provider is gated by an experimental property. The handle registry stores sessions and a validation flag in process memory. It lacks durable validity, expiry and an exposed revoke lifecycle. ZAP can handle target-side reauthentication through configured verification strategies. The MCP validation flag carries no such guarantee. The prior audit's unsupported finding for guided JSON/JWT should be read as a live-interface result with no fixture proof. The conditional source path is additional implementation evidence. [Conditional provider][jsonswitch] · [JSON configuration][jsonconfig] · [Identity validation][jsonverify] · [Handle registry][authregistry] · [Runtime evidence B01–B02][evidence]

**Native capability and dependencies.** ZAP provides form and JSON auth, context-level cookie and HTTP session handling, and configured user authentication checks. Header replay and browser auth depend on Authentication Helper and browser flows also depend on the driver. Authentication Helper 0.44.0 and browser-related add-ons appeared in the prior runnable inventory. The demonstrated blocker was the missing bound fixture profile. Script-backed auth has a separate lifecycle gap below. [ZAP authentication][zauth] · [ZAP session handling][zsession] · [Runtime evidence M03][evidence]

**Change, verification and impact.** Add a typed readback for the effective auth mode, target-origin binding and a redacted subject verdict. Define scoped handle TTL, owner, revocation and restart behavior. Keep managed secret references in operator configuration. **Complexity high** for durable, multi-worker lifecycle and medium for typed form/browser readback on an isolated engine. A local fixture can expose a benign identity endpoint and expire a synthetic session. Compare logged-out, correct-subject, wrong-subject and renewed states, including browser and HTTP separately. This would make authenticated coverage attributable to an actor and a time window.

### 2. Context scope, multiple users and application roles

**Root cause and existing implementation.** Guided profiles bind a ZAP context/user indirectly. Expert tools already list and upsert contexts and users and expose auth configuration and test. The native adapter writes context regexes and scope and reads the resulting context, and creates or updates individual users. Expert user upsert accepts a credential configuration string. There is no guided user administration or complete context/user cleanup and isolated engine-session lifecycle in the reviewed tool set. MCP tool scopes control the caller's authority to operate the server. They do not describe target-application permissions. [Expert context and users][expertusers] · [Context persistence][contextwrite] · [Native users][userwrite] · [MCP scope registry][scopes]

**Native capability and dependencies.** ZAP supports multiple users in one context and user-aware exploration. Application roles and ownership are fixture data. The optional Access Control Testing add-on handles URL/user expectations, with application-level assertions needed for business objects, functions and state changes. The add-on was absent from the prior persisted runnable inventory. That does not block standard ZAP user management. [ZAP authentication][zauth] · [ZAP Access Control Testing][zaccess] · [Runtime evidence M03 and X01][evidence]

**Change, verification and impact.** Use purpose-specific context and actor readback with credential references and owned resource lifecycle. Keep actor-role assignments and authorization expectations in the application test suite. **Complexity medium** for typed inventory and high for durable lifecycle and engine isolation. Use a disposable workspace with two ordinary fixture actor roles and an anonymous control. Verify intended role in the application's own identity response, then check normal allowed and denied outcomes against predetermined expectations. Reopen the workspace and confirm context membership and actor isolation. This enables repeatable multi-actor evidence and cleanup.

### 3. Authenticated Active DAST and execution restrictions

**Root cause and existing implementation.** Guided active execution exists. The live contract accepts a target, recurse setting, policy name, optional queue idempotency key and an auth session reference. The local source has a user-specific native active adapter and branches for direct and queued execution. Form sessions can bind to that route. Browser sessions are restricted to Client Spider, and static header-reference handles lack a reusable engine user. Experimental JSON bearer requires validated in-memory state, and the workflow rejects queued execution for that kind because restart survival is unproven. The two source-only request-selection fields also require direct authenticated execution and a previously seeded request. They do not establish a general method/parameter allowlist on the running deployment. [Live schema][evidence] · [Source tool contract][guidedattack] · [Prepared-session enforcement][sessionrules] · [Engine scan adapter][activescan]

**Native capability and dependencies.** ZAP has a native user-specific scanner API and the prior engine inventory contained active scan rules 84.0.0. User binding, configured fixtures, confirmed add-on availability and backend execution are separate prerequisites. The previous AI execution boundary excluded live active scans. There is no activation, role-correct traffic, payload coverage or detection proof from that audit. [ZAP API Reference][zapi] · [ZAP Active Scan][zactive] · [Prior runtime limits][capability]

**Change, verification and impact.** Prioritize read-only readiness, explicit capability flags, provenance and operation-status evidence for the existing authorized scanner interface. Keep active execution under the existing operator-controlled boundary. **Complexity medium** for readiness and high for durable actor binding. A recording adapter can validate typed actor/context handoff, rejected combinations, cancellation and unknown outcomes without active requests. A benign local identity fixture can establish the actor independently of the active interface. These checks qualify configuration and attribution. Actual active execution and detection remain separate qualification claims.

### 4. Custom scan policy management

**Root cause and existing implementation.** Guided accepts a named policy as input. Expert already lists and inspects policy names, category defaults and rules, and mutates individual rule enablement, strength and threshold. The adapter invokes the applicable native setters in order. A later setter failure can leave earlier mutations applied. The reviewed direct expert surface lacks policy create/delete/import/export and atomic update. The expert plan allowlist includes native policy definition, but plan execution is absent in the current guided deployment. [Expert policy tools][policytool] · [Rule readback and mutation][policyrule] · [Plan allowlist][plantypes]

**Native capability and dependencies.** Native policy management covers lifecycle operations and the Automation Framework supports named policy definitions. Rule IDs and defaults depend on the pinned engine and installed rule sets. This gap is tool coverage and mutation semantics, with no evidence of a missing active-rule bundle. [ZAP API Reference][zapi] · [ZAP Scan Policy Manager][zpolicy] · [ZAP policy job][zpolicyjob]

**Change, verification and impact.** First expose a read-only policy manifest and drift check. Preserve approved policy artifacts under operator or CI ownership. Validate configuration and record the effective policy version independently of any active execution. **Complexity medium** for read-only manifests and high for scoped lifecycle with rollback. Use a disposable engine as a configuration fixture. Compare a reviewed test policy against normalized rule readback and simulate partial failure with a recording adapter. This would make policy changes reviewable and let regression records pin the effective rule configuration.

### 5. Script management and custom scan rules

**Root cause and existing implementation.** The registered MCP groups and reviewed gateway ports have no script list/load/enable/run/result lifecycle. The existing policy hooks extend MCP governance and evidence metadata. They are independent from scripts that run inside ZAP. The expert plan allowlist rejects the native script job. Expert context auth configuration can name a native method but does not supply script artifact management or prove the script engine can run it. [Tool registration][registration] · [Extension contracts][extensions] · [Plan allowlist][plantypes] · [Expert auth configuration][expertauth]

**Native capability and dependencies.** ZAP Script Console supports multiple script types and the Automation Framework can add, run and remove supported scripts. The prior inventory included Script Console 45.20.0. Each script still needs a supported engine, reviewed artifact and compatible event lifecycle. This is principally a deliberate MCP exposure boundary. It is independent of add-on installation. [ZAP Script Types][zscripts] · [ZAP script job][zscriptjob] · [Runtime evidence M03][evidence]

**Change, verification and impact.** Expose read-only engine/script inventory and reviewed artifact identity or diagnostics. Keep execution of pre-reviewed scripts in operator-owned isolated jobs. **Complexity medium** for inventory and high for any managed execution lifecycle. A fixture can compare manifest digests and diagnostics for a preinstalled benign marker script using a disposable engine, with recording-adapter tests for unknown type and unapproved artifact. This would make approved extensions reproducible without making arbitrary code a tool input.

### 6. Requestor, sequences and deterministic business assertions

**Root cause and existing implementation.** There is no registered general request or sequence management tool. The checked-in expert Automation Framework target policy allows requestor jobs with constrained request fields and checked destinations. The same allowlist excludes native sequence jobs and script-based sequence execution. The live guided deployment lacks the plan runner. OpenAPI import registers/discovers operations through its importer and the scan-history ledger records scanner actions. Neither provides a deterministic test-case execution-and-assertion contract. [Tool registration][registration] · [Requestor and job checks][planjobs] · [Guided import][importtool] · [Ledger contract][ledger]

**Native capability and dependencies.** Native manual messages and Requester/Requestor can send selected requests. The Framework requestor can compare an expected status and report a warning. Sequence support accepts recorded workflows, with a native sequence import job. The prior runnable inventory included Requester 7.10.0 and Sequence 10.0.0. Response semantics, fixture reset, state readback and role/object assertions are application test responsibilities. [ZAP API Reference][zapi] · [ZAP requestor job][zrequest] · [ZAP sequence jobs][zsequence] · [Runtime evidence M03][evidence]

**Change, verification and impact.** Treat application-owned API and browser tests as the execution authority. MCP can inspect a versioned test manifest and accept scoped, redacted receipts for already-executed cases. **Complexity medium** for common test-case and evidence contracts, high for any generic workflow lifecycle. Use a benign two-step fixture with explicit expected status and response marker, then a case with a known mismatch and a reset/readback check. This yields deterministic pass/fail for product behavior while still allowing passive observations to be correlated.

### 7. Automation Framework plan lifecycle and execution

**Root cause and existing implementation.** The expert tools already accept an existing workspace file or inline plan, start it, read status and preview artifacts. They are excluded from guided registration. The service parses and bounds YAML, validates destinations and supported job fields, normalizes report paths into a per-run directory and materializes a ZAP-readable copy. The Java adapter calls native run and progress. There is no separate validation-only callback, stable plan export, typed per-job outcome or MCP cancellation. The supported auth subset is manual, HTTP, form or JSON and its session subset is cookie or HTTP. This restriction is separate from the experimental guided JSON bearer provider. Unsupported job types, including scripts, browser jobs and sequences, are rejected before engine execution. [Expert tools][plantool] · [Plan materialization][planprep] · [Authentication allowlist][planauth] · [Job policy][planjobs] · [Native adapter][planadapter]

**Native limitation and dependencies.** The adapter projects timestamps and info/warn/error messages. A finished response without errors is classified as unknown success in the service. Native ZAP separately documents plan validation, run, stop and progress, ordered jobs, tests and CI exit status. Whole-plan duration is capability-checked in source against ZAP 2.17.0 and Automation Framework 0.61.0 or later. It is a cooperative limit. The previous engine inventory had Automation Framework 0.62.0. Expert registration, matching filesystem paths and version/capability readback are still needed for any source-equivalent local run. No plan was executed in the live audit. [Progress interpretation][planstatus] · [Duration checks][planlimit] · [Workspace configuration][workspaceconfig] · [ZAP Automation Framework][zframework] · [Evidence H01 and M03][evidence]

**Change, verification and impact.** Put validation, version/digest inspection and artifact receipt first. Run reviewed passive plans in a dedicated native CI process, where engine exit and artifact outcomes can be captured together. A purpose-specific MCP validator and summary reader can share the supported-subset contract. **Complexity medium** for a validation-only boundary and high for managed execution and reconciliation. Verify valid, invalid and warning plans on a local static fixture, then confirm ordered jobs, passive drain, positive/negative result, expected exit and output digest across repeated runs. This delivers a versioned regression suite with independently qualified stages.

### 8. Structured runtime evidence, lifecycle and redaction

**Root cause and existing implementation.** The native finding adapter has structured alerts and message identifiers. Guided triage renders text. Expert source already has findings snapshots and diffs. The history service appends a direct `started` event. Its export is a ledger read, separate from polling a live operation, and offers bounded JSON text. Artifact chunk reads carry offsets and a SHA-256. The prior audit reconstructed and verified both formats. No tool advertised an MCP output schema. [Guided findings tools][findingtools] · [Findings snapshot and diff][findingservice] · [Start ledger event][ledger] · [Ledger export][ledgerexport] · [Chunk interface][chunk] · [Evidence M02 and I07–I14][evidence]

The JSON report code validates target scope and can copy complete accepted alert instances. This is source evidence of scope projection. The audit observed HTTP request/response fields and applied its own allowlisted projection. A digest verifies the retrieved bytes, while credential redaction and arbitrary message retrieval remain separate gaps. Browser stop provides a related lifecycle example. AJAX's native status lacks a success/failure/cancellation discriminator. The server's stop text reports success after a stop call, yet a subsequent attempt in the audit was rejected as busy. Client Spider also returned 100% after a stop request. That result requires independent coverage readback. [Scoped report projection][redaction] · [AJAX status and stop][ajax] · [ZAP Reports][zreports] · [Evidence C06–C09 and I08][evidence]

**Change, verification and impact.** Add additive, versioned outputs for operation state, engine evidence and artifact receipts. Distinguish submitted, running, stop requested, engine terminal, passive drained, coverage confirmed and case verdict. Attach run/fixture/build/case IDs, scoped message references and a redaction policy version. Use scoped allowlisted metadata before offering raw artifacts. **Complexity high** for cross-process event reconciliation and redaction, medium for schemas and typed evidence readers. Replay captured lifecycle fixtures with contradictory stop/busy results, fetch the same artifact in pages, and use synthetic credential markers to prove export redaction and workspace separation. Preserve the verified passive CSP positive/negative fixture as a coverage control. This enables CI to distinguish transport success, scanner completion and application outcomes.

### 9. Adjacent configuration and capability discovery gaps

**Root cause and existing implementation.** There is already an internal adapter for core version and installed add-ons, including an incomplete-inventory signal. No dedicated live MCP inventory tool exposed it. The passive tools provide status/wait. Per-rule settings and alert filters were absent from the live tools even though ZAP documents both. Inline OpenAPI was exposed and rejected by its explicit staging feature check. URL and staged-file imports both worked. [Engine inventory adapter][inventory] · [Passive tools][passive] · [Inline staging check][inline] · [ZAP passive scanner][zpassive] · [ZAP alert filters][zfilters] · [Runtime evidence C05, C10 and C11][evidence]

**Change, verification and impact.** Expose read-only inventory and effective passive settings with completeness/version fields. Keep passive policy writes scoped to an isolated owned workspace. Treat inline OpenAPI as an optional provisioning change for its existing adapter. **Complexity low** for inventory, medium for policy readback and scoped writes. Local fixture verification can compare enabled rule metadata and detected header condition before and after a controlled policy change. Test staged-file and inline configuration separately. This provides a reliable preflight and repeatable passive baselines.

## Alternatives

| Architecture | Where it fits | Constraint or cost | Assessment |
|---|---|---|---|
| Extend existing guided tools | Add backward-compatible status, readiness and typed evidence to normal entry points | Broader parameters can overload the intent-first contract. Existing text clients need compatibility. | Prefer additive readback and status improvements. |
| Add purpose-specific scoped MCP tools | Inventory, context/actor readback, validation-only and sanitized evidence | Each tool needs typed schemas, scope and ownership rules, an adapter and fixture qualification. Expert source reduces some work. | Best for new, narrowly defined control-plane operations. |
| Independent native Automation Framework execution | Run reviewed, versioned passive plans on an isolated CI engine with native validation and exit reporting | Pin add-ons and ZAP. CI owns runner provisioning, credentials and artifact policy. Product behavior assertions need separate tests. | Best execution engine for ZAP-native jobs. |
| MCP-assisted development with standalone CI execution | Develop and inspect fixture evidence through MCP, then run versioned application tests and reviewed ZAP plans in CI | Requires a shared manifest and evidence schema, with parity checks across environments. | Recommended architecture for reusable regression. |

The Docker-hosted passive baseline was verified in the earlier local audit. GitHub Actions execution remains unqualified. [ZAP Docker][zdocker] · [ZAP automation options][zci] · [Prior capability report][capability]

## Prioritized implementation roadmap

1. **P0 — Establish reproducible provenance.** Pin source commit, image digest, ZAP version and required add-ons. Capture deployment flags and advertised schema hashes without secrets. Compare the rebuilt release contract against the deployed tool registry. Exit when a source-only feature can be traced explicitly to an image, flag and discovered schema.
2. **P1 — Make evidence safe for CI decisions.** Add typed inventory, findings, operation status and artifact receipts. Define evidence redaction and stable fixture/run/case IDs. Exit when the passive CSP controls, cancel/busy fixture and digest/redaction checks all produce independently verifiable outcomes.
3. **P2 — Qualify authentication and context ownership.** Add managed actor readiness and verification readback, scope ownership and session lifecycle tests. Exit when local form and browser identity, expiry, anonymous control and workspace isolation are demonstrated, and any experimental provider has its own build and fixture evidence.
4. **P3 — Establish the standalone regression baseline.** Version application assertions and a reviewed passive Automation Framework plan. Validate plans independently and retain job outcomes, process exit, passive findings and digested artifacts on isolated CI runners. Exit when two clean runs give equivalent evidence and an intentional fixture mismatch fails the gate.
5. **P4 — Add purpose-specific interfaces where evidence shows a need.** Prioritize scoped context cleanup, passive configuration readback, reviewed policy inventory and plan metadata inspection. Evaluate script and sequence inspection by demonstrated demand. Maintain the existing operator boundary for active execution and defer any decision to broaden it until the prerequisite identity, scope and outcome evidence is in place.
