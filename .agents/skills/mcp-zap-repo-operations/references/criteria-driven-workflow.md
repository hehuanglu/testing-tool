# Criteria-driven assessment — version 3

This is the authoritative workflow for new assessments. It defines scope, approval, verdicts and completion; technical runner guides implement its approved cases without adding duties. Use `RUN.criteriaWorkflow.version:3`. Version 2 is retained only to read/resume historical two-approval assessments. Legacy `securityScope.workflowVersion:1`, inventory evidence version 1 and `assessmentRound.version:1` are different contracts; preserve their history and do not promote legacy statuses into v3 verdicts.

Apply the [agreed operating decisions](assessment-policy.md) for the fixed catalog, the single plan approval gate, all_cases and flexible continuation. The current user has settled these defaults; do not ask for approver identity, a risk rubric, extra budget approval or independent knowledge attestation.

## Intake and Gate 2 plan approval

The user supplies the project. Load the bundled [OWASP 2025 security catalog](owasp-2025-security-catalog.json), verify its catalog ID/version, SHA-256 `7765c109fcbcc957801351768648a1b0134e02088698bed6456dcc709af66f8c`, and 50 unique SEC IDs in catalog order, and preserve its source wording, IDs and locations separately from interpretation. Do not ask the user to supply, normalize or approve it. Account for all 50 criteria; an explicit user-selected subset bounds execution and excluded rows remain labeled separately. Do not silently select only criteria the available runner can test. Catalog coverage does not authorize unrelated targets or techniques. Discover environment/actors/fixtures from available authorized sources; ask only for consequential missing facts. Reuse an existing exact plan approval; the user need not author matrices, fixtures or JSON.

Use one [preparation subagent with coordinator review](delegation-policy.md#preparation-subagent-and-coordinator-review) for basic reconnaissance and plan drafting. The main agent coordinates, audits and returns inadequate drafts for revision with questions chosen for the actual situation; it does not use a fixed questionnaire or accept the worker's self-declared pass. Begin with basic reconnaissance chosen by the coordinator to understand the requirements' product foundation: relevant components, protocols, auth/session mechanisms, trust boundaries, ownership/sharing rules, state transitions and available observations. Keep fact, assumption and unknown distinct. Source-only discovery can proceed without runtime. New discovery traffic needs existing authority and a record in the [intake checklist](retention-stop-and-recovery.md#operator-schedule-and-crash-checkpoint). Active testing waits for the approved plan.

Project all 50 catalog requirements into criteria with stable IDs, raw/source text, product/environment boundary, oracle and its basis, applicability, sufficient evidence, finite stopping rule and excluded conclusions. For every criterion include `selected: true|false` and a specific `selectionReason`. A selected criterion also includes a concrete `testApproach` and all mapped `caseIds`; an unselected criterion has no cases and remains visible as **Out of scope for this run**. Split compound requirements into cases while retaining the parent and combination semantics. Take the fixed catalog/user business knowledge as the authoritative expected protection; source behavior cannot override it. Clarify only interpretation that genuinely prevents testing, and never change the oracle to match observed behavior. Use all_cases for every newly selected criterion and define population/sampling limits before execution.

There is no Gate 1. The fixed catalog is available from the start. Use reconnaissance to select and map criteria, then discover the inventory and dependencies needed for their tests. A new unrelated feature is a candidate, not a new obligation. A selected universal requirement such as “all protected APIs” still requires every relevant operation in its bounded inventory. Meaningful GraphQL/RPC operations may share a URL. Grouping requires a common boundary/oracle and explicit excluded conclusions; it never invents execution credit.

Prepare a finite plan with case→criterion links, objective, target/build/context, expected behavior/basis, required observation units, actor/object/state, baselines/controls, prerequisites, chosen executor and verified capability, mutations, resource ownership, cleanup/retention, permitted preparation/fallback, limitations and stopping conditions. A method boundary is an unresolved evidence dependency for applicable criteria, not a terminal verdict. Avoid Cartesian products of roles, fields and payloads unless the approved criterion requires them.

Before presenting Gate 2, complete the [coordinator's coverage and evidence audit](delegation-policy.md#preparation-subagent-and-coordinator-review) through questions, draft revisions and independent readback. Put the inventory baseline, method choices and post-discovery reconciliation in the reviewed plan so missing routes, actors or techniques remain visible during execution.

**Gate 2 — plan approval:** after the preparation agent's plan/revision loop passes coordinator review, present the complete plan with all 50 selection decisions and, for every selected criterion, the mapped all_cases and concrete test approach. Include the room for coordinator-led discovery, adapter/fixture/reader/configuration changes, equivalent admitted executors and subagents within its target/objectives/allowed effects. Wait for plan approval and retain its message/reference and binding. The plan digest includes the criteria digest, so any criteria or plan change invalidates this approval. Then execute and adapt without routine renewed approvals. Reapproval is limited to actual changes to the selected criteria/meaning, target scope or allowed effects; ordinary technical adjustments/local continuation are not new business approval gates. Preserve actual digest/action/pin/admission contracts: keep the approved envelope stable, record concrete adjustments in allocations/journals, and never relabel changed bound content as still approved. Missing execution facts may require a question; elapsed time is never approval. Continue independent approved branches while waiting.

## Shared questions and work units

Manage the assessment by criterion and execute by shared questions. Build the mapping before choosing tools:

1. For each criterion, state its oracle, bounded questions, sufficient observations and excluded conclusions. Keep its all_cases stopping rule and independently required observations.
2. Reuse a case across criteria only when the question, expectation and evidence obligations are compatible. Use the existing reciprocal `criteria[].caseIds` / `plan.cases[].criterionIds` links. If expectations or required stages differ, retain separate cases, even when the same operation can provide observations for both.
3. Group complementary cases by business journey or resource boundary to reuse context, actors, fixtures and compatible observations. Separate incompatible effects and states into sequential lanes. Follow [business work blocks](business-work-blocks.md) for cross-chat execution. A work unit is an agent-planned allocation, not a new verdict, permission, schema version or automatic scheduler. Record case/action mapping in the approved plan's existing details; do not dispatch one mutation per criterion when one authorized effect and its readback suffice.
4. Before execution, name which actual observations each operation is expected to provide for each case. Record allowed effects, executor/fixture/readback/cleanup/fallback and shared resource IDs in the plan. Check the chosen executor's real admission. There is no automatic discovery-to-live-executor adapter.
5. Execute once with durable intent/ACK/results. Retain original operation IDs and semantic readback. Link compatible observations into each case using evidenceLinks; required unit labels are not observations. Distinct input/rule/role/state objectives still need their own actual observations.
6. Review each criterion independently. A reused observation can support, contradict or leave a criterion insufficient. Shared evidence never copies `met`/`unmet` from another row, merges criteria, multiplies operations/alerts, or erases remaining work. A violation does not waive unfinished sibling cases. Historical counterexample rules remain readable but are not selected for newly prepared criteria.

Example: a non-owner GET can inform both an object-access criterion and a sensitive-data disclosure criterion. A 403 with sensitive fields in its body may answer those questions differently; inspect each oracle. It does not test logout revocation, SQL injection or every API. Reuse login/fixtures and evidence where justified; do not infer coverage from sharing a scan name.

The preparation subagent drafts these mappings and revises them in response to coordinator review; the coordinator verifies and adopts them into canonical state. Helpers check declared structure/context, not completeness of discovery or raw-to-semantic accuracy; helper success cannot replace the coordinator's situation-dependent preparation review. Accept user-supplied business knowledge as the requirement source without an independent authenticity audit; the tester remains responsible for accurate observations and application of that knowledge. Read actual results before a verdict/publication. No separate expert/reviewer signature is required.

## Versioned working representation

The coordinator adopts reviewed preparation drafts into canonical `criteriaWorkflow`; no arbitrary policy-prose parser or automatic truth oracle is claimed. Core code is `src/zap_assessment/criteria_workflow.py`:

- `version:3`, `context:{product,environment}`, `criteriaRevision`, `planRevision` and the required `catalog:{id,version,sha256,source,criterionCount}` bind a new assessment. Version 2 remains historical compatibility and retains its original two approval entries.
- `criteria` entries have `id`, `rawText`, `source`, `requirement`, `oracle`, `selected`, `selectionReason`, `applicability` (`applicable|not_applicable|unknown`), `caseIds`, and `stoppingRule` (`all_cases` for new criteria; historical `counterexample` remains supported). Selected entries also require `testApproach`; unselected entries have no cases. Product-grounded N/A additionally needs `applicabilityBasis`.
- `plan.cases` entries have `id`, `criterionIds`, `objective`, `expectedBehavior`, `expectationBasis`, `requiredEvidence`, `coverageContext` (including product/environment), `allowedLimitations`, `resourceIds`, and `effects`. Add executor/fixture/actor/fallback details needed to execute safely; document them within the approved plan, not in unapproved worker instructions.
- `plan.authority` records `source`, `target`, `allowedEffects`; optional `plan.delegation` records the approved worker boundary. The packet helper requires `plan.delegation.allowed: true` for non-coordinator execution workers. If that binding is absent, use coordinator execution where feasible; never edit an approved plan in place to enable delegation. These document actual authority, never generate it.
- For v3, `approvals` contains the sole user approval entry with `kind:plan`, `revision`, `digest`, and `source`. `approval_digest(cw,"criteria")` is an internal content identity, not Gate 1; `approval_digest(cw,"plan")` binds the catalog identity, criteria digest and plan content. Historical v2 `kind:criteria` entries remain accepted only to resume that original contract. Compute the plan digest from the reviewed artifact and retain the actual user approval source. A fabricated source string or worker `approved:true` is not permission.
- `caseResults` entries carry `caseId`, `outcome:matched|violated|null`, `basis`, semantic `evidenceLinks` and, when needed, a pending `limitation`. Legacy case outcome `not_evaluable` is read as pending; only a criterion with applicability `not_applicable` can receive that final verdict. Use the existing [evidence link contract](operational-readback.md#unit-links-and-attempt-history); `operations` remain in RUN with actual semantic readbacks.
- `criterionResults` may retain coordinator verdict claims, but the reviewer derives verdicts from cases and rejects incompatible claims. `resourceReview` contains reviewed resource/readback disposition, not a timestamp-based liveness assertion.

`validate_workflow(cw)` checks structure. `review_workflow(run)` derives plan-approval status, criterion/case results, exclusions, pending work, limits and completion eligibility. A missing or stale plan approval keeps final criterion verdicts pending even when candidate case observations exist. Structural validation cannot authenticate user consent, interpret arbitrary security semantics or prove completeness of product discovery. The coordinator retains the actual plan approval message without collecting approver identity and checks actual readback against each oracle.

CLI entry through `scripts/product_assessment.py scope`:

```sh
# Read-only; criteria digest is content identity, not an approval gate.
"$ZAP_PYTHON" -B "$ASSESSMENT_ROOT/scripts/product_assessment.py" scope criteria-digest \
  --run WORKING_RUN.json --kind criteria
"$ZAP_PYTHON" -B "$ASSESSMENT_ROOT/scripts/product_assessment.py" scope criteria-digest \
  --run WORKING_RUN.json --kind plan
"$ZAP_PYTHON" -B "$ASSESSMENT_ROOT/scripts/product_assessment.py" scope criteria-review \
  --run WORKING_RUN.json
```

Use the configured assessment environment/PYTHONPATH from [setup](setup.md). Draft/review is not dispatch. Empty work lists, caller-completed status or cached reviews do not grant completion. Recompute against current content and retained operations.

## Execute and reconcile

Choose the next useful approved case or prerequisite. Prefer related unknown-state readback, retained-result readback, ready execution, then concrete preparation. One missing actor/fixture/capability blocks its dependent cases, not independent work. Use [runner routing](runner-routing.md) to verify schema, auth, request/protocol, fixture and reader support; record `source-reviewed`, `offline-checked` or `runtime-observed` with their actual basis. A source-compatible candidate is not a runtime-qualified adapter.

Before each effect verify live target/identity/fixture and resource ownership, record durable intent, execute once, then retain IDs/ACK/outcome. Dispatch reconciles inherited RUN/operation/history uncertainty as well as its own journal; only an explicitly targeted readback may run for related pending effects. An independent object does not permit overlapping effects inside one shared scanner task; reconcile its pending action first. Consumed action IDs cannot be replayed through a new task. Read the expected stage on the exact actor/object/build. HTTP 202 or an ACK answers acceptance only; processing, persistence or delivery objectives need their corresponding readback. Auth loss and zero payloads leave active/auth evidence missing. A valid denial can answer a boundary criterion without storage readback.

Diagnose the demonstrated layer of failure and adapt the testing adapter/configuration/fixture/reader as needed for the business question within approved objectives/authority. Read existing outcomes before fixing a reader or retrying. A missing handler with feasible repair is preparation, not automatic `not_evaluable`; an actual unavailable primitive or work outside the agreed testing authority can be a concrete capability limit; adapter flexibility is not bounded by an arbitrary code-size threshold. Do not repair product vulnerabilities or launch scanner qualification to make every criterion evaluable.

The coordinator freely chooses suitable subagent use and productive work allocation without a new cost/budget justification step. Actual executor budgets/guards control effects; they are not assessment completion rules. A user-approved assessment budget can cause a justified limit only under the approved plan. Never invent a token/request quota to close early. Maintain journals/checkpoints and continue until no required feasible approved work remains. A context save, new worker, changed role or exported report does not require a user continuation prompt.

## Verdicts and completion

Work in progress has a pending verdict. Only a final supported criterion decision uses:

- **`met`:** all evidence obligations of the approved criterion are satisfied in compatible context and match its oracle. Limit the claim to the approved test scope; zero alerts does not prove source properties or general safety.
- **`unmet`:** sufficient evidence contradicts the approved oracle. For new all_cases criteria, disposition of all other planned cases is still required, including when one already violates the criterion. Counterexample early stopping applies only to preserved historical contracts, not a new default. Findings need not be repaired.
- **`not_evaluable` / Not applicable:** the named behavior/component is absent or the criterion genuinely does not apply within the approved product/deployment boundary, with concrete applicability evidence and reason `not_applicable`. This is the only terminal use of `not_evaluable`. Unknown applicability, lack of a runner, missing evidence, partial coverage, and temporary or persistent method/access/capability limits remain pending.

A pending limitation records `reason`, `basis`, `missingEvidence`, `attemptedAlternatives`, `unavailableAlternatives`, `remainingFeasibleActions`, and `reopenCondition`. It must name the missing observation and concrete cause; “more testing needed” is insufficient. Even an empty `remainingFeasibleActions` cannot close an applicable criterion. Continue independent feasible work and retain blocked obligations with their dependency/resumption condition; a checkpoint is not completion. Reasons must match `allowedLimitations` on the case. A method boundary cannot be relabeled as product inapplicability.

Applicability stays separate: product-grounded `not_applicable` is represented in the three-verdict output as `not_evaluable` with reason `not_applicable`, explicit basis and display **Not applicable**. All terminal `not_evaluable` results are N/A; do not display a separate final “Insufficient conditions to evaluate” category. Gate 2 binds this meaning. User exclusion changes the active criteria/plan revision and preserves history; the agent cannot silently remove an inconvenient criterion. Unknown applicability is not N/A.

Compound criteria use their approved case set and stopping rule. Reuse evidence only with the existing context compatibility rules. Conflicting evidence leaves required work open; do not average or vote across worker summaries. Historical `partial` does not map to `not_evaluable`; legacy `observed` does not map to `met`.

**Assessment completed:** every selected applicable criterion has a supported `met` or `unmet` verdict under its stopping rule, and every selected N/A criterion has a supported `not_applicable` basis; all unselected catalog rows have an explicit selection reason; no unresolved required evidence remains; Gate 2 matches current criteria/plan content; no relevant unresolved evidence conflict or hidden feasible required work remains; and effects/resources are reconciled or demonstrably contained with precise limitations. An unresolved selected applicable criterion prohibits completion even if no immediate testing action is available. Pending or uncontained producers prohibit completion. Retained fixtures need not be deleted when retention is authorized.

A contained unreadable effect remains unknown: record exact effect/last state, actual containment readback, unavailable reader/options, unknown impact, no-replay rule and reopen condition. An available readback must be used. Review actual journals/pending effects and known resources, not only an agent's `reviewed:true` label. Finalization is offline and never stops resources or grants replay rights.

Authoring progresses through draft criteria, criteria review, planning and plan review before execution. These phases are agent workflow descriptions, not a full automatic state machine: the current reviewer requires a structurally formed plan and computes approval/execution/completion status. Preserve actual dependencies in nextWork/limitations; its `waiting_dependency` status currently represents an explicit pause request. `stopped_by_user` requires the user's stop and leaves unknown verdicts pending. Recovery checkpoint is persisted state, not an automatic lifecycle terminal. A completed assessment can include `unmet` and `not_evaluable`; it is not a release/safety approval.

## Delegation and shared state

Apply the [delegation decision and roles](delegation-policy.md) before spawning: use the one preparation subagent and coordinator revision loop for intake/planning, then select additional business-area discovery, compatible execution groups, focused evidence review or bounded Drive delivery when useful; keep short coherent execution/readback local. Do not partition one worker per criterion or create a fixed execution team by default. The approved plan grants only work within the assessment. The coordinator owns approvals, case assignment, resource state, evidence review, final verdicts, the canonical RUN and the official Drive table. Workers cannot change approved oracle/scope, approve plans, finalize assessment or overwrite canonical reports. Only the [bounded Drive delivery worker](delegation-policy.md#drive-delivery-worker) may apply an approved write to the managed table on the coordinator’s behalf.

An execution task packet contains assessment/task/worker identity, criteria/plan revisions and digests, selected case/criterion IDs, objective/oracle, required evidence, relevant product/context facts, allowed effects, executor/working-state/private-secret references, relevant pending effects, resource ownership and result requirements. Load a fresh worker context (`fork_turns: "none"` where available); provide only the applicable references and packet, using the [selective context rules](delegation-policy.md#context-results-and-api-boundary). Never copy the parent's transcript or secret values; execution/review packets use selected catalog excerpts, while the preparation brief references the complete assigned catalog needed for coverage review. Context isolation does not isolate a scanner or product fixture.

The current make_packet helper copies an allowlist of case fields; it does not automatically include every criterion oracle, allowedLimitations, fixture, fallback or cleanup detail. Supply selected approved details through the permitted productFactsRef/workingStateRef/executorRef references and require the worker to read them before action. A packet with IDs alone is not sufficient execution context. The coordinator remains the only writer/reviewer of final conclusions.

A result packet returns actual operation/ACK references, compatible semantic observations, proposed case outcomes, limitations, pending effects, resource disposition and exact next action. The coordinator verifies revisions/digests and evidence before merge; stale output remains historical until compatibility is explicitly reviewed. Worker confidence or summary is not evidence.

These are required return semantics, not arbitrary permitted top-level merge keys: the current merge_result API accepts binding fields plus operations and caseResults only. Carry limitations within case results and actual effect/resource facts through retained operations/journals and coordinator review. Discovery/review briefs use separate task-owned results for coordinator interpretation, not executor packets or direct canonical writes.

The coordinator APIs in `criteria_delegation.py` build/validate selected-case packets, maintain persistent resource leases and merge reviewed worker results. Outstanding leased tasks block completion until release, including a lease before intent or after action reconciliation. Missing leases/journal bindings fail closed. The admitted executor must durably retain actual native ACK/IDs/results before returning; the generic coordinator journal retains execution transitions and excludes arbitrary callback response payloads. Dispatch invokes an existing admitted executor callback; packets do not import Python modules or run shell commands. One canonical writer persists RUN. Packet/merge CLI commands reload inputs and write under the retained coordinator lock; report publication holds that same reentrant lock across review, validation and publication. The result is a consistent snapshot, not a background monitor or permanent prohibition on a separately approved reopening. Direct canonical state writers must use the coordinator lock too. Include real shared scanner/session/fixture IDs in `resourceIds`; absent explicit resources, serialize by approved target. Different target URLs do not make a shared scanner isolated.

Leases survive worker failure. A timeout or expired worker does not establish that its operation stopped. Reconcile journal/ACK/native state before releasing an uncertain lease or assigning a replacement; no automatic timed takeover or mutation replay. Worker reassignment never grants additional authority. Parallel execution requires independent target objects, sessions, attribution and resources; otherwise run sequentially. Read-only planning can be independent.

When execution delegation tools or required isolation are unavailable, the coordinator executes sequentially using the same boundaries; optional discovery/evidence-review work can likewise stay local. This fallback does not waive the preparation subagent/revision loop: retain an unavailable preparation worker as its actual dependency under the delegation policy. Prefer selective loading, checkpointing and a new worker over asking the user to change chats. A real host/context limitation may still need a user handoff under [recovery](retention-stop-and-recovery.md); do not promise unlimited sessions or pretend monitoring continues without a mechanism.

## Reporting, migration and reopening

Deliver the [single-table Google Sheets output](single-table-drive-output.md) as the user-facing result, using the [handoff contract](product-assessment-handoff.md). RUN holds approved criteria/plan, verdicts, actual operations, evidence, limits and private working-state references; ALERTS holds security alerts; SCOPE_ALERTS holds only the mapped alert subset. These are internal supported projections, not three mandatory extra user deliverables. `not_evaluable` is not an alert. Do not compute a product safety percentage from `met` counts.

Track delivery separately in retained private working state: `driveOutput` records runId, actual fileId/url/worksheet identity, status (`pending|verified|outdated|failed`), lastVerifiedAt, the reviewed source revision/snapshot last synchronized, and exact remaining publishing action when needed. This is agent-maintained output state, not a new field enforced by review_workflow or an implemented exporter. Row readback, formatting, intended link access and content must be checked through connected tools. Assessment completed + Drive outdated is unfinished delivery, not a successful final handoff. Lead the handoff with the actual spreadsheet link and synchronization status.

`scope report` routes criteria workflows v2/v3 through the criteria publisher; legacy v1 callers keep their original semantics. Use `scope report --run WORKING_RUN.json --alerts ALERT_INPUT.json --output NEW_DIRECTORY` to generate an internal progress bundle, adding `--finalize-round` only after the current review is eligible. This existing flag selects the version-appropriate finalizer; it does not impose v1 whole-round closure on v2/v3. `--overwrite` replaces only the supported derived report files; preserve raw journals and historical bundles. See the handoff contract for inclusion/mapping and write guarantees.

Do not add `criteriaWorkflow` to a legacy RUN merely to close it. Prepare reviewed criteria/plan revisions, retain provenance and reuse only compatible evidence through the semantic resolver. Do not rewrite old statuses, hashes, pins or finding counts. Reopen v2 selectively when an approved scope/oracle changes, relevant build/context changes, or a named actor/fixture/capability resolves a limitation. Applicable criteria previously closed only for missing evidence must be reassessed as pending in a new retained working revision; preserve historical reports and raw evidence. Unfixed findings alone do not create new work.

## Managed working state

Use the explicit registry and committed generation as the official working location for managed v3. RUN retains the fixed catalog binding and its one content-bound Gate 2 approval. OPERATOR stays outside the approval digest. Use state-merge for coordinator-validated worker results and state-commit for other reviewed snapshot changes. A plan revision can leave a stale schedule. Rebase it explicitly with an old-to-new mapping and apply the existing approval to the new content identity. Historical v2 RUNs retain their two approvals.
