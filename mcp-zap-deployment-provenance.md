## Mode selection and runtime boundary

The documented switch is `MCP_SERVER_TOOLS_SURFACE=expert` on the separately created server instance. Expert extends the Guided tool set at startup. API-key authentication stayed enabled with freshly generated audit-only credentials. The instance used one Docker internal network, a dedicated ZAP sidecar, fresh engine state and a dedicated shared automation/report volume. Private target URLs referred to fixture services on that network. Docker did not publish an Expert port on the host. A short-lived in-network Python client called Streamable HTTP MCP. The MCP and ZAP keys and synthetic actor credentials are omitted from all deliverables. [Tagged Expert configuration](https://github.com/dtkmn/mcp-zap-server/blob/0ebe11c3ae4c17de59fde0654e19b3e35e42ca20/docs/src/content/docs/scanning/automation-framework.md) · [Tagged tool registration](https://github.com/dtkmn/mcp-zap-server/blob/0ebe11c3ae4c17de59fde0654e19b3e35e42ca20/src/main/java/mcp/server/zap/McpServerApplication.java) · [Runtime configuration evidence](mcp-zap-expert-capability-evidence.json)

The disposable sidecar's built-in health probe used its default port 8080 while this audit ran the daemon on 8090, so Docker marked the sidecar unhealthy. The MCP service was healthy, and its ZAP-backed context, scan, plan, report and inventory calls independently proved functional connectivity. Align the image health-check port with the configured daemon port for any repeat deployment. The four audit containers, internal network and shared volume were removed at completion.
