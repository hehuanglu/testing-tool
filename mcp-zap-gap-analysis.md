# MCP ZAP gap analysis

The connected deployment exposes the guided MCP surface. The [capability report](mcp-zap-capability-report.md) and [evidence bundle](mcp-zap-capability-evidence.json) govern the runtime claims. This analysis covers all 94 rows without a verified end-to-end result.

## Deployment surface versus server code

- **Deployment configuration.** The checked-in server source registers expert tool groups conditionally. It contains context and user list/upsert, authentication configuration and test, URL inventory, direct scan and policy controls, queue operations, report variants, and limited Automation Framework methods. Those source paths did not appear in authenticated discovery. The audit did not switch tool surfaces or infer live behavior from the source.
- **Automation Framework.** The bundled expert implementation accepts an existing workspace plan path or inline YAML, returns plan status, and previews artifacts. Its allowlist contains requestor, traditional Spider, active/passive configuration or wait jobs, report, exitStatus and delay. The expert tool descriptions exclude scripts, imports and browser jobs, and constrain plan destinations. No expert validation-only or plan-stop tool appeared in the reviewed registration. Native ZAP exposes a separate CLI validation operation and Automation Framework run, stop and progress API operations. [ZAP Automation Framework CLI and API](https://www.zaproxy.org/docs/desktop/addons/automation-framework/), [ZAP Framework jobs](https://www.zaproxy.org/docs/automate/automation-framework/)
- **Native capability.** Installed or runnable bundles show engine prerequisites. For example, Script Console, Authentication Helper and Automation Framework appeared in the add-on state, while their administration was absent from the live guided surface. Access Control Testing was absent from the observed runnable set. Its native user-to-URL permission model requires expected access rules and does not supply application-state assertions. [ZAP authentication concepts](https://www.zaproxy.org/docs/getting-further/authentication/concepts/), [ZAP Access Control Testing](https://www.zaproxy.org/docs/desktop/addons/access-control-testing/), [ZAP script types](https://www.zaproxy.org/docs/getting-further/scripting/script-types/)
- **Evidence quality.** The scanner ledger can preserve start records while runtime operation status reaches completion. AJAX reported stopped before a subsequent start was refused as busy. The report artifact included HTTP message data, and the audit verified its digest and scoped content. A stable result schema, a terminal-state contract and a redaction policy remain separate dependencies.
- **CI feasibility.** The verified passive sequence is noninteractive and ran against a Docker-hosted engine. GitHub Actions runner provisioning, workflow exit decisions, secret delivery and signed or retained evidence need independent qualification. [ZAP automation options and GitHub Actions](https://www.zaproxy.org/docs/getting-further/automation/automation-options/), [ZAP Docker documentation](https://www.zaproxy.org/docs/docker/)

## Priorities

1. Expose supported read-only engine inventory, stable machine-readable operation states and fixture-scoped redacted evidence. Ensure scan status can distinguish successful completion from explicit stop and backend-busy states.
2. Provide bounded context/scope lifecycle and configuration readback for isolated test workspaces. Verify prepared authentication with a target identity oracle and age/expiry controls.
3. Treat Automation Framework authoring, independent validation, execution, job status, exit verdict and artifact access as distinct interfaces. Qualify the supported subset with an isolated benign plan before using it as a CI dependency.
4. Keep role, object, function and state assertions in product-owned tests with deterministic fixtures. Use ZAP reports as evidence inputs to the same objective and test-case vocabulary.
5. Evaluate the passive subset in the intended CI environment with pinned versions, isolated destinations, bounded execution, a retained artifact policy and a clear failure signal.
