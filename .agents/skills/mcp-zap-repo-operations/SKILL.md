# MCP ZAP Repository Operations

Resolve `SKILL_DIR` from this file and `ASSESSMENT_ROOT` as `lib/zap-product-assessment/`. Prefer the configured MCP connector; source/build work needs a separately verified scanner checkout (`MCP_ZAP_REPO`). The workflow is product-neutral; individual runners have conditional product/auth/protocol support. Read [setup](references/setup.md) for installation or project changes.

Orchestrate assessment execution through configured MCP/native ZAP server operations or verified adapters. Use browser automation only when an approved case requires a real frontend journey and only through a verified allowed executor. A host session with no callable ZAP tool namespace has an exposure or registration dependency to diagnose; it does not establish that no ZAP server or engine capability exists and does not authorize ZAP Desktop, computer control, or researcher-operated manual fallback. Keep affected work pending and continue independent authorized work when the required route is unavailable. Retained prompts, deleted guides and vendor/tutorial artifacts are historical or supporting evidence, not current operating policy.

## One assessment workflow

Apply the [agreed assessment policy](references/assessment-policy.md): the bundled catalog and user business knowledge are authoritative; no approver identity collection; one plan approval gate; reconnaissance before testing; all_cases; flexible coordinator-led discovery/adapters/subagents and local continuation; consolidated Drive reporting with sharing managed by the user. Read it at intake; these choices are settled and do not need another questionnaire.

The business input is the **project**. Always load the fixed [OWASP 2025 security catalog](references/owasp-2025-security-catalog.json) (`OWASP-2025-CWE-MITRE-4.20`, version `2026-09-26`, 50 SEC IDs, SHA-256 `7765c109fcbcc957801351768648a1b0134e02088698bed6456dcc709af66f8c`); do not ask the user to supply, normalize or approve another catalog. Treat its `requirements` as the criteria source and its `zap_assessment_profile` as the method boundary: the workbook/static-review rules describe the source study and do not constrain ZAP methods or verdicts. Discover the authorized product/environment and prepare the technical inventory, actors, fixtures and mappings yourself. Account for all 50 criteria in the plan and table; label explicit exclusions without silently dropping rows. The catalog does not authorize every deployment or every possible technique.

At intake, preserve the catalog wording and scoped security behavior. Do not reinterpret its old static-review scoring contract as the ZAP oracle; follow `zap_assessment_profile` and keep native ZAP, ZAP-derived and source/config evidence separately attributable. Clarify ambiguous target/effect authority before live traffic. Plan approval does not resolve a conflict over allowed effects.

Use [criteria-driven workflow v3](references/criteria-driven-workflow.md) as the only workflow for new assessments: **project + fixed catalog → basic reconnaissance → detailed 50-criterion plan → approve plan (Gate 2) → execute/readback all selected all_cases → independent criterion verdicts → verified Drive table**. There is no Gate 1. Reuse an existing content-bound plan approval when applicable; do not add per-case/per-allocation approvals. Version 2 remains a read/resume compatibility contract with its original two approvals; never create a new v2 assessment.

Assign one [preparation subagent](references/delegation-policy.md#preparation-subagent-and-coordinator-review) to basic discovery and detailed plan drafting against the fixed catalog. The main agent coordinates and audits each draft, raises questions suited to the actual product/scope and returns insufficient work for revision until it passes that review. This internal review uses no fixed questionnaire and does not replace Gate 2.

Before Gate 2, the coordinator audits both coverage and evidence. Every one of the 50 criterion entries must state `selected`, `selectionReason`, its mapped `caseIds`, and—when selected—a concrete `testApproach` explaining how those all_cases will check it. Reconcile criteria with the discovered product surfaces in both directions, challenge gaps in use of applicable ZAP capabilities, and check that each case can distinguish the intended mechanism under the selected conditions. Reconcile actual ZAP coverage after authorized discovery. Keep unresolved prerequisites pending.

Use [business work blocks](references/business-work-blocks.md) to run and resume independent stages across chats. Before expanding traffic in a runtime lane, validate a representative native evidence link for that lane through capture, receipt, semantic linking and the closure reviewer. Continue independent source work and other admitted lanes while a lane is pending. Schedule TTL readback last.

During intake, retain private reconnaissance and approval records. Once a valid v3 plan structure exists, use the [managed state entrypoint](references/retention-stop-and-recovery.md#operator-schedule-and-crash-checkpoint). Resolve the official registry entry by assessment ID or use the retained state directory. Inspect the current generation and coordinator, recover interrupted lease metadata using the original packet, select offline, execute through existing admission, persist, and repeat. A missing or damaged pointer calls for explicit diagnosis of the known store. After each result or concrete dependency, continue the whole remaining approved workflow through review, resource reconciliation and verified delivery. Repair recoverable dependencies and choose independent ready work while waiting. Use the same spreadsheet. Apply the workflow stopping rule using the recorded authority, dependencies and resource disposition. Legacy [scope](references/assessment-scope-and-completion.md) and [representation](references/user-security-scope.md) references exist only to interpret old evidence and states, not as alternative workflows for new execution. Preserve old statuses/pins/raw. Before new work on a legacy assessment, prepare v3 criteria/plan with explicit reviewed evidence compatibility and Gate 2 approval; never promote old `partial`/`observed` labels into verdicts or rewrite historical runs.

Status, setup, reporting and skill-only work do not authorize product traffic or require invented assessment reports. Read [operational validation](references/operational-validation.md) for assigned skill/tool audits and its [subagent acceptance checks](references/operational-validation.md#subagent-operations-acceptance) when qualifying delegation. Source/test inspection is not runtime qualification.

When the user asks to preserve a reviewed case as a fixed repository regression, read
[CI regression suite](references/ci-regression-suite.md). Export is an offline artifact task:
it validates reviewed evidence and creates a deterministic candidate, but does not send
product traffic, change approval/verdict logic, or make the CI result an assessment verdict.

## Work from approved criteria

Read the canonical workflow for plan approval and stopping rules. Manage accountability by criterion; organize execution by shared questions and compatible work units. Reuse observations, not verdicts.

- Preserve original wording/source separately from interpretation. Discover only product facts and dependencies needed to interpret or test the assigned criteria. Unselected catalog clauses and unrelated inventory do not become obligations.
- Derive finite questions, expected behavior and sufficient observations from the product and criterion before choosing tools. Track names describe techniques; they do not automatically assign every endpoint, role or journey. An explicitly approved “all APIs” criterion still requires the full in-scope inventory.
- Map each question/case to every criterion it actually serves. Group operations by compatible target/build, actor, fixture, state, technique and observation stage. Retain each criterion's own oracle, required evidence and missing work; a single scan or shared request does not complete all mapped criteria. See [shared testing work](references/criteria-driven-workflow.md#shared-questions-and-work-units).
- Select [native operations](references/native-operation-routing.md) or [compatible runners](references/runner-routing.md) from actual schema/auth/fixture/readback support. Prefer suitable native operations, configuration, existing adapters, then a justified extension limited to the missing testing capability. Adapter size alone is not a scope or stopping rule. Unsupported methods remain visible; do not force cookie/SSO, GraphQL/RPC or asynchronous behavior into a foreign bearer/REST recipe.
- Execute bounded work units, using valid actors/baselines/fixtures and [semantic readback](references/operational-readback.md). Persist intent before effects and record ACK/IDs/results. Missing intended processing, zero probes or auth loss cannot supply evidence for an unanswered obligation.
- [Repair operational prerequisites](references/local-remediation-and-continuation.md) within the approved plan and continue independent work. Read retained results before retrying effects. Product vulnerability remediation and broader scanner qualification are separate assignments.
- Apply the [subagent decision and role policy](references/delegation-policy.md): use the preparation/revision role above; set explicit model and reasoning per worker when supported, and choose additional discovery, execution, evidence-review or bounded delivery workers only when useful, keeping small coherent execution/readback local. Partition by questions and security boundaries, not one worker per criterion. One coordinator owns canonical state, final verdicts and the Drive table. Use [selective context and compact handoffs](references/delegation-policy.md#context-results-and-api-boundary), then [retire workers after handoff](references/delegation-policy.md#retire-workers-after-handoff). Shared execution resources run sequentially unless explicitly isolated; a worker summary does not establish a verdict.

Use [discovery](references/product-discovery.md), [dispatch](references/operation-dispatch.md) and [responsibility reconciliation](references/responsibility-loop.md) as technical building blocks. Their legacy inventory/round statuses do not override v3 criteria/plan scope or completion. Persist recovery state throughout; [checkpoint/recovery](references/retention-stop-and-recovery.md) governs live effects and selective resume. Changing fixture, role, work unit or worker does not require a new chat.

## Evidence and completion

When one or more prior plans leave a criterion unresolved or new evidence challenges its verdict, run the [follow-up planning and execution loop](references/criteria-follow-up.md). Compare retained evidence across revisions, plan only the remaining obligations, and continue under the current approval or a reviewed revision as required. Repeat after each reviewed batch while feasible approved work remains.

Apply the [ZAP result boundary](references/zap-result-boundary.md). Native alerts and meaningful ZAP-derived observations have separate provenance. Source/config reads support discovery, fixtures and interpretation; source-only findings, dependency scans and traffic bypassing ZAP do not become ZAP-derived coverage. UI/passive/BOLA observations do not substitute for an active DAST obligation; API calls do not substitute for an approved real UI journey.

Each approved criterion ends as `met`, `unmet` or product-grounded `not_evaluable` (display **Not applicable**, reason `not_applicable`). Missing evidence, incomplete testing and method/access/capability limits remain pending; they cannot terminate an applicable criterion or complete the assessment, even when no immediate action is available. Continue feasible approved work; retain a concrete dependency and next action for blocked work. Applicability and exclusions remain explicit. `completed` means the approved assessment is accounted for, not that the product passed. Keep evidence gaps, valid counterexamples, method/access limits, resource state and separately assigned remediation distinct. Zero alerts, traffic counts, exit 0 and successful exports prove neither sufficiency nor safety. The [canonical workflow](references/criteria-driven-workflow.md#verdicts-and-completion) owns the exact rules.

## Deliver results

Deliver **one native Google Sheets file on Drive, one worksheet, one table, one row per catalog criterion**, following the [eleven-column output and visual specification](references/single-table-drive-output.md), including risk counts, Only observed, traceable per-finding evidence and explanatory notes. Read it before preparing rows or writing. Before the first Sheet write, build and review the delivery projection required there: reconcile every retained native alert and every admitted observed finding, derive per-criterion counts from finding identities rather than prose, and bind concise evidence-index links. A source note that findings exist is not a substitute for this projection. Keep intermediate progress in private working state until delivery or a user requests the current table.

Treat requests to **update progress, check status, view/show/open the table, send the table/link**, and close equivalents in Vietnamese or English as a request to synchronize the spreadsheet through the latest reviewed retained state. Reconcile already-recorded or already-running results needed to establish that current snapshot, but do not start new product traffic merely to make the report look newer. Create or update the bound Sheet, label unfinished results as interim, verify it by connected readback, then send the verified URL in the same response. Do not return a stale link without first attempting synchronization. If synchronization cannot be completed, send the existing URL when known and clearly mark it outdated or pending with the exact remaining publishing action. Human-edit synchronization/conflict handling is outside scope. All user-facing spreadsheet content, metadata, status labels, notes and supporting evidence indexes must be in English; preserve non-English catalog source text only in retained source records, not in the table. Use connected Drive/Sheets tools and their applicable skills; this is agent-operated publishing. The user manages sharing; do not change permissions.

Keep [internal state and handoff](references/product-assessment-handoff.md) separate: RUN, ALERTS and SCOPE_ALERTS remain supported internal evidence/report projections, not mandatory additional user deliverables or extra Drive tabs. The committed RUN and operator snapshot, coordinator journal and retained executor artifacts carry recovery state. Healthy controls and bare uncertainty stay in RUN; native/observed alerts and mappings keep their provenance and distinct counts. Only sanitized, necessary supporting material may be linked from the table.

Lead the final response with the spreadsheet link, whether it is interim/final, assessment status and delivery status. Distinguish evidence-based assessment completion from verified Drive delivery: missing/stale synchronization leaves delivery unfinished even if criteria are accounted for. Name exact remaining work; never rerun tests to fix publishing. A real checkpoint retains private working-state references and the exact next action. Skill-only work reports changes/checks/limits without creating a product spreadsheet or pretending to scan.

## Preserve runtime and history

Read applicable AGENTS, HEAD and dirty state. Keep product-specific routes, role semantics, selectors, auth mappings and post-state oracles in inspected adapters/product data. Preserve existing working adapters and historical plans/pins/raw; a new admitted allocation may be necessary after repair, never repinning history or replaying unknown starts/mutations.

Use real sessions. Notify the user about necessary private credential/token retention without repeated approval; keep secrets out of argv, worker prompts and shared reports. Client→MCP auth differs from ZAP→target auth; browser login does not establish native active authentication. Revalidate the live dependencies of the next action.

Respect existing authority, executor gates and measured resource reserves. Before Docker restarts verify context/daemon, exact Compose files, label-based ownership and health. Do not change network/binds/TLS/auth, broadly prune, delete history/databases, use bootstrap --force/down -v, or lower thresholds to pass. Publishing the assessment table within its authorized destination is part of this workflow; do not independently commit/push, publish unrelated material, change sharing, create chats or message others. Delegation is confined to the approved assessment and cannot expand authority or replay rights.
