## Question capability mapping and adapter example

`executor_routing.map_question_capability(question,candidates)` reuses classify_workload and choose_executor; it does not create another executor registry. The question supplies `toolName`, `arguments`, `authKind`, optional request/role, and `requiredSupport` from transport/auth/request/fixture/readback. Candidate `support` entries are `{verified:true,basis:"reviewed fact"}`. Output includes questionId, selectedExecutor or null, verified support, missingPrimitive, nextPreparation, schema/auth decisions, verificationLevel and deploymentContext where known. A schema-compatible candidate with no fixture/reader remains incomplete. Missing schema/auth fields are still rejected even when support is claimed. Without a reviewed tool mapping, the next preparation is request mapping.

For coordinator-owned Python integration, put the reviewed tool mapping in the approved action descriptor and call `Coordinator.dispatch_routed(run, packet, action, candidates, executors)`. Candidates describe the receiving session. The in-process executor registry contains admitted callbacks that revalidate binding, contract, fixtures and ownership at execution. The selected executor ID is retained with the intent. If the first route is unavailable before dispatch, a compatible registered route can execute the exact same approved action without changing its digest. A changed action descriptor still requires existing plan admission. A lost ACK keeps the original action pending and prevents switching routes to replay it. Routing is not a live CLI command or a mechanism for importing callbacks from JSON.

An action may declare a finite `fixtureOptions` list when its case binds a `coverageContext.fixtureClass`. The coordinator passes the selected `fixture_ref` separately. The admitted callback verifies ownership and equivalent actor, state and oracle before dispatch. An explicit selection is required. The selected reference is journaled against the original action ID, which still governs recovery and replay. Adding an option outside that approved list requires separate plan admission.

For a leased local scanner, `scope criteria-native-read --run RUN --packet PACKET --action-id ID` supports one explicitly approved findings summary/details or history list/get. Bind `effect: read`, `toolName`, `arguments`, `scannerResourceId` in the approved lease, and `mcpEndpoint: http://127.0.0.1:7456/mcp` in the action. The command uses the current MCP schema and optionally the private `ZAP_MCP_API_KEY` environment variable. The output references a private receipt. History list is target-filtered and bounded; get verifies the exact entry ID and target. If the ID is unknown at planning time, approve `historyEntryFrom` pointing to the list action in the same packet, omit fixed arguments on get, and pass `--history-entry-id` only after reviewing the retained list. Only IDs on exact-target rows are admitted. The list/get chain finds candidates and does not infer which start produced a candidate from target equality alone. A history result, including `started`, never proves a producer stopped. Review the receipt and actual terminal state. Persist reviewed operation evidence in RUN, then use `scope criteria-reconcile-action --run RUN --packet PACKET --action-id ID --operation-id OID --release` when appropriate. If reconciliation already finished before an interruption, use `scope criteria-release-task --run RUN --packet PACKET`. A recovery read is a distinct approved action with `readbackOf` referencing the pending action. An unknown start is never replayed by these commands.

For a new case that requires message-level ZAP provenance, set `requireZapMessageEvidence: true` in the plan. The semantic reader uses `bind_zap_message` with a reader bound to the observed scanner/session, the expected message ID and the exact verified request and response digests. The receipt binds actor, fixture, request and case and retains no request headers or bodies. The resolver keeps a case pending when that receipt or its context is missing or mismatched. Historical plans keep their original evidence contract.

Verification levels source-reviewed, offline-checked and runtime-observed require their actual basis; runtime-observed additionally needs deploymentContext. Passing schemas never upgrades the level. A source mapping or synthetic test does not qualify present deployment/auth/media behavior or turn a capability gap into outside-assignment.

`examples/question_adapter.py` is a synthetic injected-transport example with separate prepare, identity, execute, readback and cleanup. The real transport must retain original admission/binding/auth/resource checks, fixture/cleanup journaling and owned-resource authority. Execute records durable intent before dispatch, retains sanitized ACK and forbids consumed action IDs; readback calls [bounded readiness](operational-readback.md#bounded-readiness-at-the-requested-stage), then actual semantic checkers produce links. Cleanup uses only assigned owned fixtures. It is not a registered CLI plugin or a new network client; JSON cannot load/import it. Existing finite CLI continue allowlists remain unchanged. Finalsource-only setup hooks, finite body/auth/recipe support and FE caps are unchanged.
